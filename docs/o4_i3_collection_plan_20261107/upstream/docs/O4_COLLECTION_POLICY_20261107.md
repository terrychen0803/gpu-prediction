# O4 收集優先原則（2026-11-07）

依使用者最新指示，**現階段以盡量收集有用、可追溯的資料為優先，不要求每個設備上的每個模型、配置、軟體版本或完成進度都嚴格一致，也不以三台跑齊相同矩陣作為繼續工作的前提。** 這項原則取代舊規劃中「所有配置三設備皆須收齊」的收集要求。

## 現在怎麼安排工作

- GB10、RTX3090、RTX4090 各自先收能穩定執行且能增加資訊的工作。七個 A 是候選清單，不是每台必須完成的清單；某模型失敗、OOM 或不支援時，留下原因後繼續其他模型。
- 優先整理既有資料、補容易取得的缺項、盤點新算子／融合／copy／overlap，再做小型 smoke。原 21 配置、189／567 cells 是全部展開時的成本估算，不是驗收配額。
- 不要求先把其他設備補齊才分析本機結果。單設備 GI、P-only trace、P/R inventory、原生控制與失敗樣本都有用途；分別標示可回答的問題與缺少的資料。
- 共用 GitHub 程式與手冊仍是建議入口；各節點不必為了完全同版而升級環境或重收成功資料。保存實際 commit、模型／權重／輸入 hash、forward 範圍、精度、backend、計時方式與品質狀態即可追溯差異。

## 可比性在分析時檢查

RTX4090 → GB10／RTX3090 仍是主要研究方向，但不是每筆收集都必須立刻組成兩個方向。資料可先獨立保存，之後以來源與各目標**分別取可用交集**；不要求三台共同交集，也不要求每個配置都有兩個目標。

要報同一工作負載的跨設備預測或誤差時，仍須核對模型／權重、輸入、forward 範圍、精度與時間目標的可比性。不同 kernel 分解、實際 backend 與軟體版本可保留並分層解讀。若工作定義或輸入／權重不同，先作獨立 inventory 或探索，不把它們當作同一配置的成對真值。

報告每個方向實際用了哪些配置、樣本數、缺失原因及品質資格。缺配對是該次跨設備評估不可用，不表示整筆資料無價值，也不把未嘗試的配置算成預測失敗；已宣告評估範圍內的失敗仍保留分母。比較方法用同一可用子集；只有兩方向都有可比較範圍時，才另報有明確權重的彙總。

## 不被本次調整改寫的資料意義

保留 raw、失敗與歷史版本；調整 batch、尺寸、模型、權重、精度或 forward 範圍時記成新 variant／signature。這不需要為追齊其他節點停工，但不能沿用舊 ID 混算。

GI、profiler span 與 host 時間各自記錄。Trace 不完整或 Reference 尚未驗證的資料可用於明示限制的探索／工具診斷，原品質狀態照實保留；不能因放寬收集對齊就自動改成 verified。本次沒有解除辨識器、N0 或 ITER 正式訓練的既有限制。

## 程式與文件版本

本次是文件／執行優先順序調整，未修改 collector、parser、模型或凍結資產驗證器。固定工程 tag `o4-unified-engineering-v1-20261106` 繼續重現原協定；本原則作為其外部規劃補充。現有工具驗證完整 frozen_A 的行為照舊，`--workload` 可選已支援的個別模型；尚不支援的資產變體先登記需求，不能改 manifest 繞過驗證，也不宣稱已支援任意資產或缺失模式。
